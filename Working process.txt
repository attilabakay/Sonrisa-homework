Typed source interfaces (com.sonrisa.homework.matching.sourcedata) — NewsData/MarketData/EmergencyData records, built at match time from DataEntry.rawJsonData + DataSource.fieldMapping by SourceDataMapper. Nothing persisted, matching the datamodel doc's "in-memory-only construct" note.

Matching engine (MatchingEngine) — runs synchronously right after a DataEntry is saved (DataEntryServiceImpl.create), per workflow.md's "creation triggers Matching." It:
- pulls only alerts that are active and whose owning user is active (workflow.md §1's enforcement rule)
- evaluates per type: keyword-contains for NEWS, ABOVE/BELOW threshold for MARKET (percent-change deliberately skipped — the source docs flag that as an open design question, not decided), exact region match for DISASTER/WEATHER
- on match, resolves the alert's Sender → channel adapter, sends, and records a NotificationAttempt with the real status/error

Verified live: booted the app, ran all three alert types through real HTTP calls — matching and non-matching entries for each type, one EMAIL sender and one SLACK sender. Got exactly 3 NotificationAttempt rows (correct alerts fired, non-matches didn't), each FAILED with a genuine, distinguishable error (SMTP connection refused vs. Slack DNS error) — showing the "call-success only" status semantics work as intended once real credentials are supplied.

Also added: an admin GET /api/alerts/user/{userId}/all endpoint for "which alerts belong to which user" visibility (mvp final.md §5), and a spring.mail.host placeholder so the mail bean actually initializes.
