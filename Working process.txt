Implemented — all six entities from datamodel final.md, each with model/DTO(s)/repository/service/controller, restricted to exactly the operations workflow.md allows:

- User — register, get all, get by id, deactivate (no update/delete)
- Sender — full CRUD (not covered explicitly by workflow.md, so kept flexible for "picks/creates")
- DataSource — create, get all/by id, update (link/apiKey/fieldMapping), deactivate, delete (blocked with 409 if it has DataEntry history)
- DataEntry — create (manual/admin for now, since the polling job isn't built), get all/by source/by id — no update/delete
- Alert — create, get active-by-user, get by id, deactivate (the real "delete"), hard delete (allowed but discouraged)
- NotificationAttempt — create, get all, get by alert — append-only, no update/delete

Also added, since nothing was testable without it:
- H2 in-memory datasource + JPA config in application.properties
- A minimal SecurityConfig (permit-all, BCrypt PasswordEncoder bean) so Spring Security's auto-generated login doesn't block every request — real login/session handling per mvp final.md §1 is still unbuilt
- A GlobalExceptionHandler mapping not-found/conflict/validation errors to proper HTTP statuses

Verified: compileJava succeeds, and I ran the app end-to-end via curl through the full chain — register → duplicate-email 409 → sender → data source → data entry → alert → active-alerts-by-user → notification attempt → deactivate alert (drops from active list) → deactivate+delete data source (409 due to entry history) → deactivate user. All behaved per spec.
